# Módulo 2 – Hot Desks v0.1

## Introducción

El módulo Hot Desks ofrece la posibilidad de reservar mesas disponibles para trabajar a todos los usuarios del CRM, gestionar sus reservas y recibir confirmaciones por correo electrónico. 

La vista inicial ofrece tres opciones al usuario:
  1- Elegir una franja temporal de reserva contenida en las dos semanas siguientes.
  2- Hacer una reserva "rápida", que seleccionando la planta donde se quiere trabajar, te devuelve mesas disponibles para las próximas dos horas.
  3- Modificar la reserva acortando la duración o eliminarla, siempre que quede al menos dos horas hasta el inicio de la reserva. 

Todas las modalidades hacen una reserva personal, que necesita por lo tanto validación previa del usuario mediante el login. 

Todas las mesas están numeradas con un identificador, así el usuario puede elegir entre las disponibles en caso de tener preferencias. 

## Base de datos

Para el correcto uso de este módulo, se han creado tres tablas a la base de datos:

- `hottable` : identifica cada mesa y guarda su planta y capacidad. Contiene también el atributo `is_hot` para poder activar y desactivar si la mesa se puede reservar.
- `reservation` : contiene un identificador y guarda la mesa y la franja temporal.
- `reservation_user` : por cada reserva, guarda el usuario que ha reservado (especialmente útil si en algún momento se quiere permitir que se pueda reservar para varios usuarios a la vez).

Este módulo también accede a la tabla users para guardar correctamente la reserva y a las tablas de logs.

## Flujo general de uso

### 1. Consulta de disponibilidad
- Petición desde `index.html`
- `serveAPI` recibe datos (`floor`, `startTime`, `endTime`, `capacity`)
  - Caso form: `floor` = all (4).
  - Caso img: `startTime` = now, `endTime` = now + 2, `capacity` = 1.
- Se consultan mesas `hot` que cumplan con la condición floor.
- De esas mesas, se buscan las reservas que coincidan en la franja de tiempo pedida.
  - Si no tienen ninguna reserva, se devuelven esas mesas al FrontEnd sin más consultas.
  - Si tienen alguna reserva:
    - Se comprueba que ninguna reserva sea del usuario, ya que no puede tener dos activas al mismo tiempo.
    - Se calcula cuantos usuarios coinciden en la franja de tiempo deseada en la misma mesa, para saber si quedan los asientos deseados libres (tan solo consulta si los asientos están libres, la reserva es personal).
- Se devuelven mesas disponibles filtradas por capacidad y conflictos en `showTables.html`.

### 2. Creación de reserva
- `serveAPI` recibe la mesa seleccionada. 
- Se crea la entrada de reserva para la BD (`table_id`, `start_date`, `end_date`).
- Se crea la entrada reservation_user para la BD (`reservation_id`, `user_id`).
- El usuario visualiza `confirmation.html` y se le pide un correo electrónico. 
- Se envía correo de confirmación al usuario.

### 3. Modificación o eliminación de reserva
- Petición desde `index.html`
- `serveAPI` recibe petición `GET` y devuelve las entradas de las reservas del usuario.
- El usuario selecciona la reserva a modificar y `serveAPI` recibe el ID de la reserva.
- Se muestra la información de la reserva y se permite editarla al usuario:
  - Modificar las horas de entrada/salida, siempre acortando la reserva. El servidor recibe una petición `PUT`.
  - Cancelar la reserva. El servidor recibe una petición `DELETE`.

## Endpoints

### `POST /module/proxy/module2/api/bd`

- Si incluye `table_id`: crea una reserva
- Si incluye `floor`, `startTime`, `endTime`: devuelve disponibilidad

- Si incluye campo `GET`: 
  - `fetchMyReservations`: Devuelve reservas próximas del usuario
  - `fetchAllMyReservations`: Devuelve el historial completo de reservas del usuario
  `fetchAllReservations`: Devuelve el historial completo de reservas, solo accesibles por el rol 'admin' o 'manager'. 
  
- Si incluye campo `PUT`: modificación de reserva existente
- Si incluye campo `DELETE`: elimina reserva existente
