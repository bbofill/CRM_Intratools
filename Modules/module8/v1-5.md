# Módulo 8 — Budgeting

## Introducción

El **módulo 8** implementa el sistema de **Budgeting** de CRMIntratools. Su objetivo principal es permitir que los usuarios creen, consulten y gestionen solicitudes relacionadas con gastos o necesidades presupuestarias asociadas a proyectos del CRM.

El módulo permite crear solicitudes de diferentes categorías:

- **Travel**: viajes, desplazamientos, instituciones de destino, fechas, equipaje, preferencias y documentación personal necesaria.
- **Registration**: inscripciones a eventos, congresos o reuniones, incluyendo factura o documento de pago.
- **Accommodation**: alojamiento asociado a una actividad o viaje.
- **Equipment**: solicitudes de equipamiento informático o material.
- **Other**: otros gastos no incluidos en las categorías anteriores.

La solicitud se registra como una entidad general y una o varias partes específicas. Cada parte representa una categoría seleccionada y contiene sus datos propios. A partir de ahí, la solicitud entra en un flujo de validación por responsables: IP/supervisor, Projects, Accounting, IT o Gerència, según el tipo de solicitud y las condiciones del proyecto.

El módulo también incluye:

- Área de configuración de usuarios con permisos de gestión.
- Listado de solicitudes enviadas por el usuario.
- Área de gestión para responsables.
- Vista administrativa de todas las solicitudes.
- Exportación completa o filtrada a Excel.
- Gestión de facturas pendientes.
- Gestión de certificados de asistencia.
- Recordatorios automáticos mediante cron.
- Registro de auditoría cifrado con cadena de hashes.
- Exportación de certificados PDF de auditoría.

## Base de datos

El módulo se apoya en varias tablas del sistema. La comunicación con la base de datos se realiza mediante el servicio interno de base de datos, usando peticiones JSON con operaciones de tipo `GET`, `POST`, `PUT` y, en algunos casos, `DELETE`.

### Tabla `budget_requests`

Representa la solicitud general o combinada. Una entrada de esta tabla puede contener una o varias partes en `budget_parts`.

Campos principales usados por el módulo:

| Campo | Descripción |
|---|---|
| `id` | Identificador interno de la solicitud combinada. |
| `id_intern` | Identificador visible generado con formato `año-proyecto-id`, por ejemplo `2025-PROJ-00012`. |
| `people_id` | Usuario/persona que crea la solicitud. |
| `creation_date` | Fecha de creación. |
| `projects_response` | Indica si Projects/Gerència ha validado la solicitud. |
| `projects_response_date` | Fecha de validación por Projects/Gerència. |
| `acc_or_it_response` | Indica si Accounting o IT ha validado la última fase. |
| `acc_or_it_response_date` | Fecha de validación por Accounting o IT. |
| `denied_comment` | Motivo de rechazo. |
| `canceled` | Marca de cancelación. |
| `cancelation_motive` | Motivo de cancelación introducido por el usuario. |
| `prev_request` | Referencia a una solicitud anterior cuando se modifica una solicitud rechazada. |

### Tabla `budget_parts`

Contiene cada categoría concreta de una solicitud. Por ejemplo, una misma solicitud puede tener una parte de `travel`, otra de `registration` y otra de `accommodation`.

Campos principales:

| Campo | Descripción |
|---|---|
| `id` | Identificador de la parte. |
| `id_combined` | Relación con `budget_requests.id`. |
| `category_id` | Categoría de la parte: `1 travel`, `2 registration`, `3 accommodation`, `4 equipment`, `5 other`. |
| `project_id` | Proyecto asociado. |
| `ip_id` | Responsable/IP/supervisor asociado. |
| `ip_response` | Validación por IP. |
| `ip_response_date` | Fecha de validación por IP. |
| `purpose` | Propósito, evento o descripción breve. |
| `observations` | Observaciones adicionales. |
| `travel_fromPlace` | Lugar de origen para viajes. |
| `wherePlace` | Lugar de destino o alojamiento. |
| `institution` | Institución de destino. |
| `fromDay` | Fecha de inicio. |
| `untilDay` | Fecha de finalización. |
| `registration_invoice` | Indica si la inscripción dispone de documento/factura. |
| `registration_type` | Tipo de documento de inscripción: factura o documento de pago. |
| `equipment_category` | Categoría del equipamiento. |
| `other_price` | Rango de precio asociado a equipment/other. |
| `luggage_type` | Tipo de equipaje solicitado. |
| `luggage_weight` | Peso de equipaje facturado. |
| `seat_preference` | Preferencia de asiento. |
| `time_preference` | Preferencia horaria. |
| `travel_area` | Área del viaje: España, Unión Europea o fuera de la UE. |

### Tabla `request_files`

Guarda los adjuntos asociados a una parte de la solicitud.

| Campo | Descripción |
|---|---|
| `request_id` | Relación con `budget_parts.id`. |
| `file_path` | Ruta del archivo almacenado. |
| `type` | Tipo lógico del archivo, por ejemplo factura actualizada. |

Los archivos se guardan físicamente dentro de:

```text
Uploads/03_BudgetReq/<project_id>/
```

### Tabla `budget_attendance_certificates`

Se usa para controlar los certificados de asistencia pendientes para solicitudes aprobadas de viaje o inscripción.

Campos principales:

| Campo | Descripción |
|---|---|
| `id_combined` | Solicitud combinada. |
| `file_uploaded` | Indica si el certificado ya se ha subido. |
| `file_path` | Ruta del certificado. |
| `uploaded_at` | Fecha de subida. |
| `last_reminder_at` | Última fecha de recordatorio. |
| `reminder_count` | Número de recordatorios enviados. |

### Tabla `budget_audit_logs`

Registra una traza de auditoría por cada acción relevante del flujo presupuestario.

| Campo | Descripción |
|---|---|
| `id` | Identificador del log. |
| `combined_id` | Solicitud combinada. |
| `part_id` | Parte de la solicitud, si aplica. |
| `category_id` | Categoría afectada. |
| `previous_hash` | Hash anterior de la cadena. |
| `current_hash` | Hash calculado para el registro actual. |
| `payload` | Payload cifrado y codificado. |
| `created_at` | Fecha de creación del log. |

La cadena de auditoría funciona como una cadena enlazada: cada log incluye el hash anterior y calcula su propio hash a partir del hash anterior y del contenido cifrado. Esto permite detectar manipulaciones o rupturas de integridad.

## Estructura de archivos

### BACK-END

```text
module8workers/
```

#### `server.go`

Inicializa el servidor del módulo 8 y registra las rutas principales:

```text
/api
/Uploads
```

El servidor se levanta con TLS usando `ListenAndServeTLS` y el puerto definido en la configuración `Module8ServerPort`.

También inicializa el cron de certificados de asistencia mediante:

```go
InitAttendanceCertificatesCron(mC.Module8ApiKey, httpClient)
```

#### `api.go`

Centraliza el routing del backend. Todas las operaciones del módulo entran por `/api` y se seleccionan mediante el parámetro `action`.

Ejemplo:

```text
/module/proxy/module8/api?action=getSentRequests
```

El flujo general de `serveAPI` es:

1. Lee la API key.
2. Verifica la API key con `verifyAPIKey`.
3. Crea un cliente HTTP con timeout.
4. Si el entorno está en desarrollo, usa cliente inseguro para certificados locales.
5. Lee `action` desde la query string.
6. Ejecuta el handler correspondiente.
7. Si la acción no existe, devuelve `400 Bad Request`.

`serveUpload` actúa como proxy seguro para servir archivos subidos desde la ruta `/Uploads`.

#### `types.go`

Define las estructuras compartidas por el módulo:

- `Config`: configuración del módulo.
- `AuthCookieClaims`: datos de autenticación extraídos de cookie/token.
- `SavedFile`: estructura para archivos validados y guardados.
- `RequestPayload`: datos recibidos desde el formulario de Budgeting.
- `ExistingPart`: estructura auxiliar para editar solicitudes existentes.
- Mapas de categorías.
- Estructuras de correos HTML.
- Estructuras de certificados de asistencia.

También define las extensiones y MIME types permitidos:

```text
.pdf, .png, .jpg, .jpeg, .webp
```

#### `utils.go`

Es el archivo principal de lógica de negocio del módulo. Contiene:

- Gestión de accesos.
- Obtención de proyectos.
- Validación de formularios.
- Creación de solicitudes.
- Inserción de partes por categoría.
- Consulta de solicitudes enviadas.
- Cancelación de solicitudes.
- Subida de facturas pendientes.
- Modificación de solicitudes.
- Cálculo de permisos.
- Consultas para área de gestión.
- Vista administrativa de todas las solicitudes.
- Exportaciones Excel.
- Aprobaciones y rechazos.
- Notificaciones internas.
- Envío de correos HTML.
- Funciones auxiliares de normalización, formato y estado.
- Certificados de asistencia.

#### `files.go`

Implementa la validación y guardado seguro de archivos.

Controles implementados:

- Tamaño total máximo de request: `25 MB`.
- Tamaño máximo por archivo: `10 MB`.
- Máximo de archivos por clave: `5`.
- Validación de extensión.
- Validación de MIME real mediante `http.DetectContentType`.
- Comprobación de coincidencia MIME/extensión.
- Creación de directorio por proyecto.
- Nombre de archivo generado con prefijo, username y timestamp.
- Permisos restrictivos en carpetas y archivos.

Ejemplo de nombre generado:

```text
invoice_jdoe_20250203_101522.pdf
```

#### `cron.go`

Configura una tarea diaria en zona horaria `Europe/Madrid`.

La tarea se ejecuta cada día a las **08:15** y revisa solicitudes aprobadas de viaje o inscripción cuyo periodo ya ha finalizado y que todavía no tienen certificado de asistencia.

Si procede, envía recordatorios y actualiza la información de seguimiento.

#### `budget_audit.go`

Implementa el sistema de auditoría del módulo.

Funcionalidades principales:

- Construcción de payloads de auditoría.
- Cifrado de payloads con GPG.
- Codificación base64 del payload cifrado.
- Cálculo de hash SHA-256.
- Enlazado de registros mediante `previous_hash` y `current_hash`.
- Verificación de integridad de la cadena.
- Obtención de logs por solicitud/parte.
- Exportación de certificado PDF.

#### `imports.go`

Agrupa funciones comunes usadas por el módulo:

- Comunicación con servicios internos.
- Envío de correos simples o con adjuntos.
- Extracción de usuario y rol.
- Handler `checkRole`.
- Funciones auxiliares compartidas con el resto del módulo.

## Flujo general de uso

### 1. Entrada al módulo

El usuario accede a la vista principal de Budgeting.

El frontend carga:

- Permisos del usuario.
- Badge de notificaciones.
- Certificados de asistencia pendientes.
- Proyectos disponibles.
- Vista por defecto `New request`.

Según sus permisos, se muestran u ocultan las secciones de gestión.

### 2. Creación de una solicitud

El usuario selecciona una o varias categorías.

Reglas principales:

- `Travel`, `Registration`, `Accommodation` y `Other` pueden combinarse.
- `Equipment` es mutuamente excluyente con el resto.
- Cada categoría genera su propio acordeón dinámico.
- Cada parte tiene proyecto asociado.
- Si el proyecto tiene un IP/responsable disponible, se asigna automáticamente o se permite seleccionarlo.

Al enviar:

1. El frontend construye un `FormData`.
2. Añade `categories` como JSON.
3. Añade los campos visibles del formulario.
4. Añade adjuntos si existen.
5. Valida campos obligatorios.
6. Para viajes, valida teléfono y documento.
7. Envía `POST submitRequest`.

El backend:

1. Extrae el usuario autenticado.
2. Parsea el formulario multipart.
3. Construye `RequestPayload`.
4. Resuelve IPs si no se reciben desde frontend.
5. Valida datos obligatorios por categoría.
6. Valida y guarda adjuntos.
7. Crea una fila en `budget_requests`.
8. Genera `id_intern`.
9. Crea una o varias filas en `budget_parts`.
10. Guarda rutas de adjuntos en `request_files`.
11. Crea logs de auditoría.
12. Envía notificaciones y correos al usuario y responsables.

### 3. Flujo de aprobación

El flujo se basa en tres niveles principales.

#### Fase 1 — IP / responsable

Cada parte tiene un `ip_id`. Si el usuario que crea la solicitud es el mismo IP, la parte se marca como aprobada automáticamente por IP.

Si no, aparece en el área de gestión del IP correspondiente.

Cuando el IP aprueba:

- Se marca `ip_response = 1`.
- Se rellena `ip_response_date`.
- Se crea log de auditoría.
- Se notifica a la siguiente fase.

#### Fase 2 — Projects / Gerència

Una vez aprobada por IP, la solicitud pasa a Projects o Gerència según los permisos y condiciones del proyecto.

Projects/Gerència revisa la solicitud, puede modificar datos permitidos, aprobar o rechazar.

Al aprobar:

- Se marca `projects_response = 1`.
- Se rellena `projects_response_date`.
- Se decide la siguiente fase según la categoría:
  - Travel, registration, accommodation y other pasan a Accounting.
  - Equipment pasa a IT.

#### Fase 3 — Accounting / IT

Accounting gestiona viajes, inscripciones, alojamientos y otros gastos.

IT gestiona solicitudes de equipamiento.

Al aprobar:

- Se marca `acc_or_it_response = 1`.
- Se rellena `acc_or_it_response_date`.
- La solicitud queda completamente aprobada.
- Se envían notificaciones y correos finales.

### 4. Rechazo de solicitudes

Desde el área de gestión, un responsable puede rechazar una solicitud.

El rechazo exige un comentario obligatorio. Este comentario se guarda en `denied_comment` y se comunica al usuario para que pueda corregir la solicitud.

El sistema distingue el actor del rechazo:

- Rechazo por IP.
- Rechazo por Projects.
- Rechazo por Gerència.
- Rechazo por Accounting.
- Rechazo por IT.

Cada rechazo genera:

- Actualización de estado.
- Log de auditoría.
- Notificación interna.
- Correo al usuario y, si procede, a responsables implicados.

### 5. Modificación de solicitudes

El usuario puede modificar solicitudes desde **Sent requests** cuando la lógica de estado lo permite.

Casos principales:

- Solicitud rechazada: se puede revisar el motivo, corregir datos y reenviar.
- Inscripción con documento de pago: queda pendiente de factura y se permite subir factura posteriormente.
- Solicitud no aprobada todavía: se pueden modificar datos antes de que finalice el flujo, según el estado.

El frontend detecta cambios comparando los valores originales con los actuales. Si no hay cambios ni archivos nuevos, evita enviar una petición innecesaria.

### 6. Cancelación de solicitudes

Desde **Sent requests**, el usuario puede cancelar una solicitud.

El frontend pide confirmación y solicita un motivo obligatorio. El backend marca:

```text
canceled = 1
cancelation_motive = <motivo>
```

La solicitud cancelada deja de aparecer en la lista de solicitudes enviadas activas y se notifica a los responsables que ya habían intervenido en el flujo.

### 7. Facturas pendientes

En solicitudes de inscripción, el usuario puede indicar que tiene un documento de pago pero no la factura final.

En ese caso:

- La solicitud puede quedar pendiente de factura.
- En **Sent requests** aparece la acción para subir la factura.
- La subida se realiza con `addInvoice`.
- El backend guarda el archivo y actualiza la parte de inscripción.

### 8. Certificados de asistencia

Cuando una solicitud de viaje o inscripción está completamente aprobada y su fecha de fin ya ha pasado, el sistema requiere un certificado de asistencia.

Funcionamiento:

1. El backend detecta candidatas con `acc_or_it_response = 1` y fecha final pasada.
2. Si no existe certificado subido, se registra como pendiente.
3. El frontend muestra badge y popup informativo.
4. El usuario accede a **Attendance certificates**.
5. Sube el archivo correspondiente.
6. El backend guarda el archivo y marca el certificado como subido.

Además, un cron diario revisa los certificados pendientes y envía recordatorios.

### 9. Vista administrativa y exportaciones

La vista **All requests** permite consultar todas las solicitudes del sistema.

Incluye:

- Búsqueda por ID interno.
- Filtros avanzados.
- Ordenación por columnas.
- Exportación total a Excel.
- Exportación filtrada a Excel.
- Acceso a certificados de auditoría.

Los Excel contienen una fila por cada parte (`budget_parts`) y repiten los datos generales de la solicitud (`budget_requests`).

### 10. Auditoría

Cada acción relevante genera un registro en `budget_audit_logs`.

Acciones auditadas principales:

- Creación de partes de solicitud.
- Aprobación por IP.
- Aprobación por Projects/Gerència.
- Aprobación por Accounting/IT.
- Rechazo.
- Modificación relevante.
- Cambios de estado.

El payload de auditoría se cifra con GPG, se codifica en base64 y se enlaza mediante hashes.

La vista administrativa puede:

- Verificar la cadena de hashes.
- Detectar si un registro ha sido manipulado.
- Descargar un PDF de certificación de auditoría.

## Validaciones implementadas

### Validaciones generales

- La solicitud debe tener al menos una categoría.
- Cada categoría debe tener los campos obligatorios definidos.
- Las fechas de fin no pueden ser anteriores a las fechas de inicio.
- El proyecto es obligatorio en todas las categorías.
- El responsable/IP es obligatorio en todas las categorías.
- El frontend valida campos visibles; el backend vuelve a validar antes de guardar.

### Validaciones por categoría

#### Travel

Campos obligatorios:

- Origen.
- Destino.
- Institución.
- Fecha de inicio.
- Fecha de fin.
- Propósito.
- Proyecto.
- IP/responsable.
- Tipo de equipaje.
- Preferencia de asiento.
- Preferencia horaria.
- Área del viaje.

Reglas adicionales:

- Si el área es fuera de la UE, se exige pasaporte.
- Se avisa si el documento caduca antes del final del viaje.
- Se puede adjuntar invitación o documentación justificativa.

#### Registration

Campos obligatorios:

- Evento.
- Tipo de pago/documento.
- Proyecto.
- IP/responsable.

Puede incluir:

- Factura.
- Documento de pago.
- Fechas del evento.
- Observaciones.

Si se adjunta documento de pago, el sistema permite subir la factura final posteriormente.

#### Accommodation

Campos obligatorios:

- Lugar.
- Fecha de inicio.
- Fecha de fin.
- Propósito.
- Proyecto.
- IP/responsable.

#### Equipment

Campos obligatorios:

- Categoría.
- Descripción.
- Proyecto.
- IP/responsable.

Reglas:

- `Equipment` es mutuamente excluyente con el resto de categorías.
- Si se selecciona `Other` dentro de equipment, se habilitan campos de descripción y rango de precio.
- Para importes altos se muestra aviso de posible procedimiento de contratación pública.

#### Other

Campos obligatorios:

- Descripción.
- Proyecto.
- IP/responsable.

Puede incluir rango de precio. Para importes altos se muestra aviso de posible procedimiento de contratación pública.

### Validación de archivos

Archivos permitidos:

```text
.pdf, .png, .jpg, .jpeg, .webp
```

Restricciones:

- Máximo `10 MB` por archivo.
- Máximo `5` archivos por campo en backend.
- Validación de extensión.
- Validación de MIME real.
- Rechazo si el contenido no coincide con la extensión.

## Seguridad

### Autenticación y autorización

- Todas las acciones del backend requieren API key válida.
- El usuario se obtiene a partir de la sesión/cookie/token.
- Las vistas se adaptan al rol y permisos del usuario.
- `configuration.html` redirige a `/main` si el usuario no es admin.
- `Management area` solo se muestra a IPs, Projects, Accounting, IT o Gerència.
- `All requests` se muestra a perfiles administrativos o de gestión avanzada.

### Seguridad de archivos

- Validación estricta de extensión y MIME.
- Tamaño limitado.
- Directorios creados con permisos restrictivos.
- Archivos guardados con nombres generados, no con el nombre original directo.
- Servido de archivos mediante ruta proxy `/Uploads`.

### Auditoría

- Los eventos relevantes se guardan cifrados.
- Cada registro se enlaza al anterior con hash SHA-256.
- La verificación detecta cambios en payload, hash actual o hash anterior.
- Los certificados PDF se generan solo si la cadena es válida.

## Consideraciones de implementación

### Solicitud combinada + partes

La decisión de separar `budget_requests` y `budget_parts` permite que una solicitud tenga varias categorías y que cada categoría tenga su propio responsable, proyecto, adjuntos y estado de IP.

### Formulario dinámico

El frontend no mantiene todos los campos visibles desde el inicio. En su lugar:

1. El usuario selecciona categorías.
2. `budgeting.js` llama a los builders de `categoryOptions.js`.
3. Se renderizan acordeones solo para las categorías activas.
4. Se aplican validaciones y dependencias.
5. Se serializan solo campos relevantes.

### Gestión por permisos

El backend no devuelve una lista única de gestión. Construye la lista en función de los permisos reales del usuario.

Esto permite que un mismo usuario pueda ver varias colas si tiene varios roles, por ejemplo IP y Accounting.

### Archivos en memoria en frontend

El frontend gestiona los archivos seleccionados en estructuras temporales para:

- Mostrar listas de archivos seleccionados.
- Evitar duplicados.
- Permitir quitar archivos antes de enviar.
- Enviar solo los archivos correctos en `FormData`.

### Auditoría independiente del estado visible

La auditoría no depende solo del estado actual de la solicitud. Cada acción crea un registro independiente, cifrado y enlazado. Por eso se puede reconstruir el histórico aunque la solicitud haya cambiado de estado posteriormente.

## Resumen final

El módulo 8 de Budgeting es un módulo completo de gestión presupuestaria que cubre todo el ciclo de vida de una solicitud: creación, validación, aprobación, rechazo, cancelación, adjuntos, certificados posteriores, exportación y auditoría.

La implementación combina:

- Backend Go con routing centralizado por `action`.
- Formularios frontend dinámicos en JavaScript modular.
- Validaciones duplicadas en frontend y backend.
- Gestión de permisos por roles y flags de usuario.
- Almacenamiento seguro de archivos.
- Notificaciones internas y correos HTML.
- Exportaciones Excel.
- Cron de recordatorios.
- Auditoría cifrada y verificable con hash chain.

Este diseño permite que el módulo sea flexible para el usuario final, pero también trazable y controlado para administración, Projects, Accounting, IT y Gerència.
