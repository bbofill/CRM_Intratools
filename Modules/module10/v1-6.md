# Módulo 10 — Service Commissions

## Introducción

El **módulo 10** implementa el sistema de **Service Commissions** de CRMIntratools. Su objetivo principal es permitir que los usuarios creen, consulten, revisen, validen y exporten comisiones de servicio asociadas a viajes y gastos.

El módulo está conectado con el módulo de **Budgeting**, ya que puede crear comisiones de servicio a partir de viajes presupuestarios ya aprobados. También permite crear viajes manuales cuando la comisión no proviene de una solicitud previa de Budgeting.

El módulo permite gestionar:

- **Viajes existentes** aprobados en Budgeting y pendientes de comisión de servicio.
- **Viajes manuales** creados directamente desde el módulo.
- **Gastos del investigador** asociados a la comisión.
- **Revisión económica** mediante tablas de tarifas correspondientes a las diferentes becas.
- **Validación por personal de proyectos**.
- **Validación final secuencial** por solicitante, responsable de proyecto y Geréncia.
- **Generación de PDF borrador**.
- **Firma digital del PDF final**.
- **Exportación de PDFs firmados**.
- **Exportación de datos y documentos en ZIP**.
- **Gestión de tablas de precios para dietas, alojamientos y kilometraje**.
- **Auditoría cifrada con cadena de hashes**.
- **Notificaciones internas y correos HTML**.

El flujo completo cubre el ciclo de vida de una comisión de servicio: creación, revisión de gastos, aprobación inicial, validaciones finales, generación documental, firma, exportación y marcado como exportada.

## Base de datos

El módulo se apoya en tablas propias y en tablas compartidas del sistema. La comunicación con la base de datos se realiza mediante el servicio interno de base de datos, usando peticiones JSON con operaciones `GET`, `POST` y `PUT`.

### Tabla `service_commisions`

Representa la comisión de servicio principal.

Campos principales usados por el módulo:

| Campo | Descripción |
|---|---|
| `id` | Identificador interno de la comisión. |
| `people_id` | Persona solicitante de la comisión. |
| `creation_date` | Fecha de creación de la comisión. |
| `people_category` | Categoría del solicitante, guardada como `G1`, `G2` o `G3`. |
| `request_travel_id` | Viaje existente procedente de `budget_requests`, si aplica. |
| `new_travel_id` | Viaje manual creado en `comm_travels`, si aplica. |
| `status` | Estado actual de la comisión. |
| `updated_at` | Última fecha de actualización. |

Estados principales:

| Estado | Significado |
|---|---|
| `submitted` | Comisión enviada por el usuario y pendiente de revisión. |
| `under_review` | Comisión en revisión por Projects/Gerència, normalmente tras revisar gastos. |
| `final_review` | Comisión aprobada inicialmente y pendiente de validaciones finales. |
| `approved` | Comisión validada completamente y con PDF final firmado. |
| `rejected` | Comisión rechazada. |
| `exported` | Comisión ya exportada por Projects/Gerència. |

### Tabla `comm_travels`

Guarda viajes manuales creados desde el módulo cuando la comisión no se basa en un viaje existente de Budgeting.

Campos principales:

| Campo | Descripción |
|---|---|
| `id` | Identificador interno del viaje manual. |
| `id_intern` | Código visible generado para el viaje o comisión manual. |
| `from_where` | Lugar de origen. |
| `to_where` | Lugar de destino. |
| `destination` | Destino o institución de destino. |
| `purpose` | Motivo del viaje. |
| `start_date` | Fecha de inicio. |
| `end_date` | Fecha de fin. |
| `project` | Proyecto asociado. |
| `file_path` | Ruta del certificado de asistencia subido para el viaje manual. |

Los viajes manuales requieren certificado de asistencia en el momento de crear la comisión.

### Tabla `service_commission_expenses`

Contiene los gastos asociados a una comisión. Cada comisión debe tener al menos un gasto.

Campos principales:

| Campo | Descripción |
|---|---|
| `id` | Identificador del gasto. |
| `service_id` | Relación con `service_commisions.id`. |
| `type` | Tipo de gasto. |
| `amount` | Importe declarado o calculado. |
| `transport_method` | Medio de transporte, cuando aplica. |
| `description` | Descripción del gasto. |
| `purpose` | Origen lógico del gasto: `user` o `center`. |
| `departure_date` | Fecha de salida del gasto o tramo. |
| `return_date` | Fecha de retorno. |
| `departure_time` | Hora de salida. |
| `return_time` | Hora de retorno. |
| `per_diem_breakdown` | Detalle JSON de dietas, comidas, cenas, desayunos y eventos. |
| `distance_km` | Distancia en kilómetros para kilometraje. |
| `mileage_rate` | Tarifa por kilómetro. |
| `related_task` | Tarea relacionada revisada o heredada de Budgeting. |
| `location_label` | Localización usada para gastos de centro. |
| `excluded` | Marca de exclusión lógica del gasto. |

Tipos de gasto principales:

| Tipo | Uso |
|---|---|
| `transport` | Transporte ordinario. |
| `mileage` | Kilometraje con captura obligatoria. |
| `per_diem` | Dietas calculadas por reglas de días, comidas y cenas. |
| `accommodation` | Alojamiento revisado contra tarifas. |
| `budget_travel` | Gasto de centro importado desde Budgeting para viaje. |
| `budget_registration` | Gasto de centro importado desde Budgeting para inscripción. |
| `budget_accommodation` | Gasto de centro importado desde Budgeting para alojamiento. |

### Tabla `comm_files`

Guarda los archivos adjuntos asociados a un gasto.

| Campo | Descripción |
|---|---|
| `expense_id` | Relación con `service_commission_expenses.id`. |
| `file_path` | Ruta del archivo almacenado. |
| `type` | Tipo lógico del archivo. |

Tipos de archivo usados:

| Tipo | Descripción |
|---|---|
| `receipt` | Ticket o justificante del gasto. |
| `payment_proof` | Comprobante de pago o transferencia. |
| `mileage_proof` | Captura o prueba obligatoria para kilometraje. |
| `travel` | Archivo relacionado con el viaje. |

Los archivos de gastos se guardan físicamente dentro de:

```text
Uploads/04_ServiceCommissions/<project_code>/<expense_type>/
```

Los certificados de asistencia de viajes manuales se guardan en:

```text
Uploads/03_BudgetReq/<project_code>/
```

### Tabla `service_commission_documents`

Guarda la documentación generada para una comisión.

| Campo | Descripción |
|---|---|
| `id` | Identificador del documento. |
| `service_id` | Relación con `service_commisions.id`. |
| `draft_pdf_path` | Ruta del PDF borrador generado tras la aprobación inicial. |
| `signed_pdf_path` | Ruta del PDF final firmado o ZIP final firmado. |
| `document_hash` | Hash SHA-256 del borrador. |
| `signed_document_hash` | Hash SHA-256 del documento final firmado. |
| `status` | Estado documental: por ejemplo `draft` o `signed`. |
| `created_at` | Fecha de creación. |
| `updated_at` | Fecha de actualización. |

Cuando hay un único documento final, `signed_pdf_path` apunta a un PDF. Cuando la comisión genera más de un documento, por ejemplo nómina y transferencia, puede apuntar a un ZIP con varios PDFs firmados.

### Tabla `service_commission_approvals`

Gestiona la cadena de aprobación final después de la revisión inicial por Projects.

| Campo | Descripción |
|---|---|
| `id` | Identificador de la aprobación. |
| `service_id` | Relación con `service_commisions.id`. |
| `approver_type` | Tipo de aprobador. |
| `approver_people_id` | Persona que debe validar. |
| `status` | Estado de la aprobación, normalmente `pending` o `approved`. |
| `message` | Mensaje opcional del aprobador. |
| `created_at` | Fecha de creación. |
| `updated_at` | Fecha de actualización. |
| `approved_at` | Fecha de aprobación. |

Tipos de aprobador:

| Tipo | Descripción |
|---|---|
| `applicant` | El solicitante confirma la comisión tras revisión de Projects. |
| `project_responsible` | Responsable del proyecto valida la comisión. |
| `management` | Gerència realiza la validación final. |

Las aprobaciones son secuenciales. No se activa una aprobación posterior hasta que las anteriores están aprobadas.

### Tabla `service_commission_audit_logs`

Registra una traza de auditoría cifrada para acciones relevantes del flujo.

| Campo | Descripción |
|---|---|
| `id` | Identificador del log. |
| `service_id` | Comisión asociada. |
| `timestamp` | Fecha y hora del evento. |
| `action` | Acción registrada. |

La cadena comienza con `GENESIS`. Cada nuevo registro calcula su hash a partir del hash anterior y del payload cifrado, permitiendo detectar alteraciones.

## Estructura de archivos

### BACK-END

```text
module10workers/
├── api.go
├── server.go
├── types.go
├── utils.go
└── imports.go
```

#### `server.go`

Inicializa el servidor del módulo 10 y registra las rutas principales:

```text
/api
/Uploads
```

El servidor se levanta con TLS mediante `ListenAndServeTLS`, usando el puerto definido en `Module10ServerPort`.

#### `api.go`

Centraliza el routing del backend. Todas las operaciones entran por `/api` y se seleccionan mediante el parámetro `action`.

Ejemplo:

```text
/module/proxy/module10/api?action=my-commissions
```

El flujo general de `serveAPI` es:

1. Lee la API key desde la request.
2. Verifica la API key con `verifyAPIKey`.
3. Crea un cliente HTTP con timeout de 30 segundos.
4. Si el entorno está en desarrollo, usa un cliente inseguro para certificados locales.
5. Lee `action` desde la query string.
6. Ejecuta el handler correspondiente.
7. Si la acción no existe, devuelve `400 Bad Request`.

`serveUpload` actúa como proxy seguro para servir archivos subidos desde la ruta `/Uploads`.

#### `types.go`

Define estructuras compartidas:

- `Config`: configuración del módulo.
- `AuthCookieClaims`: datos de autenticación extraídos de la cookie cifrada.
- `Log`: estructura usada para logs.

La configuración incluye parámetros específicos de firma PDF:

- `PDFSignerCommand`.
- `PDFCertificatePath`.
- `PDFCertificatePassword`.
- `PDFSignatureReason`.
- `PDFSignatureLocation`.

- Listados de comisiones del usuario, Projects y aprobadores finales.
- Detalle completo de comisión.
- Revisión de gastos.
- Gestión de tablas de tarifas.
- Guardado de revisiones de precios, kilometraje, anticipos y edición administrativa.
- Aprobación inicial por Projects.
- Creación de flujo de aprobación final.
- Generación de PDF borrador.
- Firma digital de PDFs finales.

## Flujo general de uso

### 1. Entrada al módulo

El usuario accede al módulo 10.

El frontend inicializa:

- Notificaciones.
- Modo de viaje.
- Formulario de comisión.
- Bloque de gastos.
- Workspace de comisiones.
- Gestión de tarifas si el usuario tiene permisos.

Después llama a `session` para conocer:

- Usuario autenticado.
- Rol.
- Permiso `access_projects`.
- Permiso `access_gerencia`.
- Si puede revisar comisiones.
- Si puede ver certificados de asistencia.
- Si puede gestionar tarifas.

### 2. Selección del viaje

El usuario puede elegir dos modos.

#### Viaje existente

El módulo muestra viajes que cumplen estas condiciones:

- Pertenecen al usuario autenticado.
- Proceden de Budgeting.
- Están aprobados.
- No están cancelados.
- Son viajes finalizados.
- No tienen una comisión activa asociada, salvo comisiones rechazadas.
- Tienen categoría de viaje en `budget_parts`.

Antes de crear la comisión, el sistema exige que exista certificado de asistencia subido en `budget_attendance_certificates`.

#### Viaje manual

El usuario introduce manualmente:

- Origen.
- Destino.
- Institución o destino principal.
- Propósito.
- Fecha de inicio.
- Fecha de fin.
- Proyecto.
- Certificado de asistencia.

El backend crea una fila en `comm_travels` y genera un código interno con el formato:

```text
COMM-<año>-<proyecto>-<id_servicio>
```

### 3. Creación de gastos

El usuario añade uno o varios gastos.

Cada gasto incluye:

- Tipo.
- Descripción.
- Importe o distancia, según el tipo.
- Fechas y horas, cuando aplica.
- Método de transporte, cuando aplica.
- Desglose de dietas, cuando aplica.
- Tickets o justificantes.
- Comprobantes de pago.
- Prueba de kilometraje para `mileage`.

El backend valida que exista al menos un gasto y que cada kilometraje tenga archivo de prueba.

### 4. Envío de la comisión

Al enviar el formulario:

1. El frontend valida viaje, gastos, importes y archivos.
2. Construye un `FormData` con datos de viaje y gastos.
3. Envía `POST create-commission`.
4. El backend obtiene el usuario autenticado.
5. Parsea el formulario multipart.
6. Determina si el viaje es existente o manual.
7. Si es existente, comprueba certificado de asistencia.
8. Si es manual, crea `comm_travels`.
9. Crea la fila en `service_commisions` con estado `submitted`.
10. Inserta gastos en `service_commission_expenses`.
11. Guarda archivos en `Uploads/04_ServiceCommissions`.
12. Inserta metadatos de archivos en `comm_files`.
13. Importa gastos de centro desde Budgeting si aplica.
14. Envía correo y notificación a Projects.

### 5. Revisión por Projects / Gerència

Usuarios con rol `admin`, `access_projects` o `access_gerencia` pueden revisar comisiones.

Desde el modal de revisión pueden:

- Ver datos del viaje.
- Ver solicitante, proyecto, destino, fechas y propósito.
- Revisar categoría de persona.
- Revisar tarea relacionada.
- Revisar gastos declarados.
- Añadir gastos de centro.
- Eliminar o excluir gastos de centro.
- Revisar tarifas de dietas y alojamiento.
- Revisar kilometraje.
- Editar descripción, transporte, importe y anticipo.
- Ver tickets, comprobantes y pruebas.
- Previsualizar PDF.
- Aprobar o rechazar la comisión.

Una comisión solo se puede aprobar si todos los gastos activos han sido revisados.

### 6. Revisión económica de gastos

El módulo distingue varios tipos de revisión.

#### Dietas y alojamiento

Se revisan mediante tablas configuradas en **Rates Management**. La revisión guarda:

- Tabla aplicada.
- Grupo.
- Territorio.
- Importe calculado.

#### Kilometraje

Se revisa guardando:

- Distancia en kilómetros.
- Tarifa por kilómetro.
- Importe calculado.

#### Anticipos y edición administrativa

Projects/Gerència puede guardar:

- Anticipo al investigador.
- Descripción revisada.
- Importe revisado.
- Método de transporte revisado si el gasto lo permite.

Cada guardado de revisión pone la comisión en estado `under_review`.

### 7. Aprobación inicial

Cuando Projects aprueba una comisión:

1. Se comprueba que los gastos estén revisados.
2. Se actualiza la categoría de persona si se ha modificado.
3. Se actualiza la tarea relacionada si se ha modificado.
4. Se crea un log de auditoría `projects_initial_approval`.
5. Se genera un PDF borrador.
6. Se guarda el borrador en `service_commission_documents`.
7. Se crean aprobaciones finales en `service_commission_approvals`.
8. Se cambia el estado de la comisión a `final_review`.
9. Se notifica al siguiente aprobador.

### 8. Validaciones finales

El flujo de validación final es secuencial:

1. Solicitante (`applicant`).
2. Responsable de proyecto (`project_responsible`).
3. Gerència (`management`).

El endpoint `stakeholder-commissions` devuelve las comisiones pendientes para el aprobador actual. Cuando un aprobador valida:

1. Se comprueba que su aprobación esté activa.
2. Se marca la aprobación como `approved`.
3. Se guarda mensaje opcional.
4. Se crea log de auditoría.
5. Se notifica al siguiente aprobador.

Cuando todas las aprobaciones están completadas, se genera el PDF final firmado.

### 9. Generación y firma de documentos

El módulo genera primero un PDF borrador con los datos revisados. Antes de firmar el documento final:

1. Lee el PDF borrador.
2. Verifica que el hash del borrador coincide con `document_hash`.
3. Verifica la cadena de auditoría.
4. Obtiene el último hash de auditoría.
5. Genera una página de integridad con hashes.
6. Añade esa página al PDF.
7. Normaliza el PDF.
8. Firma digitalmente con la configuración del módulo.
9. Guarda el PDF firmado o un ZIP con varios PDFs firmados.
10. Guarda `signed_document_hash`.
11. Cambia la comisión a `approved`.
12. Notifica a Projects.

Cuando existen documentos separados para nómina y transferencia, se firman por separado y se empaquetan en un ZIP final.

### 10. Descarga y exportación de PDFs

El módulo permite:

- Descargar el PDF final de una comisión.
- Previsualizar el PDF borrador durante revisión.
- Exportar un PDF firmado individual.
- Exportar varios PDFs firmados en un ZIP.
- Marcar comisiones aprobadas como `exported` tras la exportación.

Si se exporta una única comisión, el backend devuelve un PDF o ZIP según el tipo de documento final. Si se exportan varias, devuelve `signed_service_commissions.zip`.

### 11. Exportación de datos y documentos

El panel de exportación permite filtrar por:

- Fecha desde.
- Fecha hasta.
- Proyecto.
- Persona.
- Tipo de documento.

Tipos de documento soportados:

| Tipo | Contenido |
|---|---|
| `tickets` | Tickets o justificantes (`receipt`). |
| `payment_proofs` | Comprobantes de pago (`payment_proof`). |
| `mileage` | Pruebas de kilometraje (`mileage_proof`). |
| `commission_pdf` | PDF final firmado o ZIP final firmado. |

La exportación genera un ZIP con estructura:

```text
<project>/<person>/<commission_code>/<document_type>/<file>
```

Si no hay comisiones firmadas para los filtros, el backend devuelve:

```text
No signed commissions found for these filters
```

Este caso se considera informativo, no un error funcional del negocio.

### 12. Gestión de tarifas

La pestaña de tarifas está disponible para usuarios con permiso de gestión.

Permite:

- Crear tablas de tarifas.
- Editar tablas existentes.
- Desactivar tablas.
- Definir filas por territorio, grupo e importe.
- Definir filas de dietas con tipo de comida.

Estas tablas se usan durante la revisión de gastos para calcular importes finales.

## Validaciones implementadas

### Validaciones generales

- Todas las acciones requieren API key válida.
- El usuario se obtiene desde la cookie cifrada `CRMINTRATOOLS`.
- La creación de comisión exige al menos un gasto.
- Los gastos de kilometraje requieren prueba adjunta.
- Un viaje existente requiere certificado de asistencia.
- Un viaje manual requiere datos completos y certificado de asistencia.
- Los revisores deben tener rol o permisos adecuados.
- Una comisión no se puede aprobar inicialmente si quedan gastos sin revisar.
- Las aprobaciones finales se realizan en orden secuencial.
- La firma final verifica el hash del borrador y la cadena de auditoría.

### Validaciones de viaje existente

Un viaje existente solo aparece disponible si:

- Pertenece al usuario.
- Está aprobado.
- Es de categoría viaje.
- La fecha de fin ya ha pasado.
- No tiene una comisión activa asociada.

### Validaciones de viaje manual

Campos obligatorios:

- Origen.
- Destino.
- Institución o destino principal.
- Propósito.
- Fecha de inicio.
- Fecha de fin.
- Proyecto.
- Certificado de asistencia.

### Validaciones de gastos

Campos obligatorios generales:

- Tipo.
- Descripción.
- Importe o distancia según tipo.

Reglas específicas:

| Tipo | Validación |
|---|---|
| `mileage` | Exige distancia positiva y prueba de kilometraje. |
| `per_diem` | Requiere fechas y desglose de dietas. |
| `transport` | Puede exigir método de transporte. |
| `accommodation` | Se revisa con noches y tarifas. |
| Gastos estándar | Exigen importe válido cuando aplica. |

### Validación de documentos finales

Antes de firmar:

- El borrador debe existir.
- El hash del borrador debe coincidir con `document_hash`.
- La cadena de auditoría debe ser válida.
- El firmador PDF debe generar un documento legible.

|---|---|---|
| `submitted` | Comisión enviada y pendiente de revisión. | Usuario / Projects. |
| `under_review` | Comisión revisada parcialmente o con cambios de revisión. | Projects/Gerència. |
| `final_review` | Comisión aprobada inicialmente y pendiente de validación final. | Solicitante, responsable, Gerència. |
| `approved` | Comisión validada completamente y firmada. | Sistema tras validación final. |
| `rejected` | Comisión rechazada. | Projects/Gerència. |
| `exported` | Comisión firmada y exportada. | Projects/Gerència. |

## Seguridad

### Autenticación y autorización

- Todas las acciones del backend requieren API key válida.
- El usuario se extrae desde la cookie cifrada.
- Los permisos se calculan con rol y flags de usuario.
- `admin` y `superadmin` tienen permisos avanzados.
- `access_projects` habilita revisión y gestión de tarifas.
- `access_gerencia` habilita revisión y validación de gestión.
- La visualización de certificados de asistencia se restringe a perfiles autorizados.
- La descarga de documentos finales comprueba que el usuario sea solicitante o aprobador asociado.

### Seguridad de archivos

- Las rutas se normalizan antes de servir o exportar.
- Las rutas deben estar dentro de `../../Uploads`.
- Los nombres de descarga se sanitizan.
- Los ZIP evitan colisiones mediante nombres únicos.
- Los archivos subidos se guardan bajo rutas controladas por proyecto y tipo de gasto.

### Seguridad documental

- El PDF borrador se hashea con SHA-256.
- El PDF final firmado también se hashea.
- La firma final incluye una página de integridad.
- La cadena de auditoría debe ser válida antes de firmar.
- El payload de auditoría se cifra con GPG y se codifica en base64.

## Consideraciones de implementación

### Integración con Budgeting

El módulo reutiliza viajes aprobados de Budgeting. Esto evita duplicar información y garantiza que solo se creen comisiones sobre viajes ya validados y finalizados.

### Comisiones manuales

Cuando no existe una solicitud previa de Budgeting, el módulo permite crear un viaje manual. Este viaje se guarda en `comm_travels` y se vincula a la comisión mediante `new_travel_id`.

### Gastos de usuario y gastos de centro

El módulo separa gastos según su origen:

- `user`: gastos introducidos por el investigador.
- `center`: gastos asumidos por el centro o importados desde Budgeting.

Esto permite calcular totales separados y revisar cada bloque de forma independiente.

### Revisión antes de aprobar

La aprobación inicial exige que todos los gastos activos tengan revisión. Esto evita generar el PDF borrador con importes incompletos.

### Validación final secuencial

Las aprobaciones finales se activan en orden. El sistema evita que Gerència apruebe antes de que el solicitante y el responsable hayan validado.

### Firma con integridad

La firma final no se limita a firmar el PDF. Antes se añade una página de integridad con hashes del documento y de la auditoría. Esto permite relacionar el documento final con el historial auditado.

### Exportación y estado `exported`

Cuando Projects/Gerència exporta documentos firmados, las comisiones aprobadas se marcan como `exported`. Las comisiones ya exportadas pueden seguir descargándose si se seleccionan explícitamente.

## Resumen final

El módulo 10 de Service Commissions gestiona el ciclo completo de las comisiones de servicio dentro de CRMIntratools.

La implementación combina:

- Backend Go con routing centralizado por `action`.
- Frontend JavaScript modular.
- Integración con Budgeting.
- Creación de viajes manuales.
- Gestión dinámica de gastos.
- Revisión económica con tablas de tarifas.
- Flujo de aprobación inicial y final.
- Generación y firma digital de PDFs.
- Exportación de documentos firmados y adjuntos.
- Notificaciones internas y correos HTML.
- Auditoría cifrada y verificable mediante cadena de hashes.

Este diseño permite que el usuario cree una comisión de forma guiada, mientras Projects, responsables y Gerència mantienen control sobre revisión económica, validación documental, firma y trazabilidad del proceso.
